## Dependency graph, not a fixed ladder

A useful root is **identified inputs → boot/menu**. From it, develop parallel proof branches:

- **Persistence/economy:** file/resource serialization → ordinary Career roundtrip and refusal boundaries → dealer transaction → owned-Car/Part state → race settlement persistence.
- **Runtime lifecycle:** resource/VM creation and failure rollback → Car/controller/camera ownership → Garage/City cycles → cleanup after activity interruption.
- **Simulation/presentation:** validated driving fixture → control/contact/sleep boundaries → HUD/camera/visibility; scheduled sound and real audio can develop alongside this.

Race setup joins Car eligibility, scene/trigger/AI/timer paths and economy. Its terminal outcomes rejoin persistence and cleanup. A validated ordinary-load fixture can shorten repeated tests without requiring a fresh new-Career/dealer walk for every candidate. Keep a separate cold path to prove those earlier transitions. Resource/VM failure seams and sound teardown can be tested before driving; they should not be artificially delayed behind “finish a Night Drag Race.”

A milestone result should identify scenario/branch, Stock authority and exception decision if any, exact fixtures/builds, preconditions, action/application point, observations, numerical tolerance/time bound, result and retained evidence. Independently report **implemented**, **Port execution observed**, **Stock comparison observed**, and **verified for this contract**. One passing branch must not promote its entire family. These labels and graph remain proposals for the interview.

### A reviewable proof record

Every proof should carry:

- **Question and boundary:** one observable proposition, whole-program or isolated helper; variant (successful/refused/interrupted/repeated/restarted), explicit excluded behavior and predecessor contracts.
- **Authority:** Stock Executable identity, Stock script class/tree/node/source-line or decompile anchor; any explicit exception decision. Mark direct script evidence, observed Stock result, inferred rule and proposed assertion separately.
- **Arrange/action:** immutable source identities, private starting state, controls/hooks and their addresses/values, exact action source, requested and actual application times, Stock schedule identity and units, random-call/thread mapping where relevant.
- **Observe:** semantic event/state/file/resource identifiers, input receipt and consumption, clock/frame/physics-step correlation, render/capture boundary, audio observation route; finite retention bounds and missing/drop counters. Raw pointer equality across processes is not an observable-state contract.
- **Judge:** independently established same-side repeatability, equality or justified numerical tolerance and deadline, first divergence, failure/refusal outcome, retained artifacts and complete/incomplete status. Missing evidence cannot become pass. A quirk is a result to match unless the exception record says otherwise.
- **Status:** separately mark source rule located, observation mechanism validated, Stock case observed, Port case observed and comparison verified. A lower-seam proof must identify which whole-program contract consumes it; it cannot silently promote the parent.
