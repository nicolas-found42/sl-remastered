## What exists

- **Isolated native scenario Runs:** [`run_native.py`](../../tools/parity/run_native.py#L105) records executable/script hashes, bounded data identity, copied initial save, selected environment, command, process result and readiness milestones; checks source save preservation; retains logs/screenshots/Cartrace. It forces neither seed nor timestep itself: `SLRR_FORCE_SEED` is inherited. Its ordinary zero exit means completion/preservation, not Parity or even passing telemetry criteria. Launcher tests mostly use a fake external process ([tests](../../tools/parity/test_run_native.py)); actual application Runs are a separate acceptance seam.
- **Forced Seed:** [`random.cpp`](../../src/natives/random.cpp#L10) validates one unsigned 32-bit override and applies it on each `Math.randomize`; otherwise truncates the supplied performance clock. Both branches log assigned seed. PRNG state advances in `mathRandom`; opt-in draw tracing exists. A single override is not a sequence of seeds by VM thread/call; neither thread identity nor random-call order is present in the ordinary seed event.
- **Time remains variable:** [`startup_probe.cpp`](../../tools/startup_probe.cpp#L1699) polls actions by steady-clock elapsed time. Readiness waits pause script time only. The probe feeds measured previous-frame duration to player input and `TimerState::advanceFrame` with max delta 0.1 and max substep 0.02 ([call](../../tools/startup_probe.cpp#L1984)); duration includes rendering and `SDL_Delay(1)` ([measurement](../../tools/startup_probe.cpp#L2216)). [`advanceFrame`](../../src/natives/game_type.cpp#L3386) subdivides the actual duration, including a final variable slice and tiny-partial accumulation. The 0.02 limit is not a fixed timestep. Timer delivery, VM scheduling, scene readiness, and action receipt can therefore differ across Runs.
- **Native failure replay:** [`replay.py`](../../tools/replay.py) restores a verified initial-save snapshot when available (otherwise copies current save with an explicit mismatch warning), chooses recorded physical input over a script, verifies executable identity, and forces a single actual recorded seed when all logged seeds agree. It replays elapsed-time input and compares normalized failure causes, not complete state or trajectories; it refuses stock Wine records. Multiple distinct seeds cannot be reproduced by this mechanism.
- **Stock captures:** [`capture/README.md`](../../tools/wine/capture/README.md) describes D3D back-buffer capture and DirectInput injection/receipt logs. [`scripted_flow.sh`](../../tools/wine/capture/scripted_flow.sh) uses presentation count, sleeps, mouse coordinates and wall-time key holds; a present count is not a simulation tick or semantic readiness signal. The newer external-input stock experiment is separate retained one-attempt automation, not this generic runner ([record](../../tools/parity/stock-capture-evidence.md#L190)). Neither path exposes shared Stock/Port random state or aligned simulation/input ticks.
- **Narrow original-code comparisons:** `tools/wine/*_oracle.sh` and `tools/parity/road-*` run fingerprint-checked Stock code in helper processes and compare bounded inputs/results. E.g. [road-path](../../tools/parity/road-path/README.md) compares final native/Stock float values for the installed City dataset, with explicit x87 context. [Oracle run records](../../tools/wine/ORACLE-RUNS.md) retain commands, input/output hashes, deadlines and failures. These are useful function/data Parity evidence, not deterministic whole-game execution. The [seed helper](../../tools/parity/stock-seed-helper.md) substitutes timer and initializer in private helper memory; it does not capture live-game seed or choose a Car.
- **Frame comparator:** [`compare_frames.py` documentation](../../tools/parity/README.md#L1) explains image hashes, dimensions and RGB differences with explicit optional resize. It does not establish equivalent states, align moments, or produce a valid gameplay Parity score.

## Measurable now, missing seams, proposed experiments

**Now:** bounded native readiness/total latency, input-to-physics-frame relationships, seed and requested Car, control transitions, trajectory/velocity/contact anomalies, screenshot-to-last-physics-row correlation, executable/data/save identity and preservation. Stock presently supports bounded visual/flow observations and measured external input posting; narrow Stock helpers offer much stronger numerical comparisons for their explicit function contracts.

**Missing for deterministic paired game Runs:** confirmed common save/load state and selected Car; Stock seed/thread/random-call observation; common logical time and step sequence; input application at agreed simulation boundaries; comparable snapshots/events with stable semantic identifiers rather than pointers; a first-divergence comparator with declared numerical tolerances; captured environmental/render/audio/instrumentation effects. A fixed timestep in the Port alone would create a reproducible diagnostic schedule, but would not establish that the Stock Executable used it or preserve stock timing behavior.

Candidate experiments for discussion (not executed or implementation-approved):

1. Reprocess existing same-binary native benchmark records to locate earliest divergence in input frame, step duration, random request and player state, retaining exact identities. This can separate scheduling variation from physics differences without another game launch.
2. Repeat one bounded native scenario from identical fixtures and seed with identical tracing; measure first divergence and trace-on/off timing impact. Require a declared outcome/tolerance before calling repeatability sufficient.
3. Validate the native baseline save through ordinary Stock menu entry, then establish a common Car and visible starting state. This is necessary before treating equal throttle duration or pixel difference as a comparison.
4. Propose a bounded, reviewed live Stock observation of seed calls, timestep and actual input consumption, preserving process/thread/call order and assessing perturbation. Existing [seed observation notes](../../tools/parity/seed-observation.md) explicitly report unsuccessful debugger automation; do not assume it works. Existing [walk detour](../../tools/wine/capture/README.md#L24) has unresolved installation/review limitations and is not a turnkey clock/input hook.
5. Start diagnostic comparisons at the smallest Stock helper contract that can exercise a suspected mismatch, before considering a whole-game deterministic harness. Keep synthetic helper evidence distinct from normal gameplay evidence.
